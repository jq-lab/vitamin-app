## 2. 产品身份

Vitora 是一款私密的 iOS 身体节律陪伴 app，服务对象是想看懂自己每日状态、但不想被任务系统推着走的年轻女性。

Vitora 也是用户面对的 AI assistant。它的工作不是装饰页面，而是把健康数据、周期上下文、用户补充和晚间反馈翻译成用户能理解的每日状态，并从用户的选择和反馈中学习。旧 `Luna` 只允许作为历史证据或内部代码迁移债务，不再作为产品角色名。

核心循环是学习循环：

1. 早晨：Vitora 给出今日状态和一个清晰下一步。
2. 白天：用户正常生活，需要时补充记录。
3. 选择：Vitora 在需要建议时给出很小的当日行动。
4. 晚间：Vitora 回访今天发生了什么，并对比干预前后效果。
5. 次日：Vitora 根据反馈让建议更贴近用户。

Vitora 不能变成：

- 打卡工具
- todo 工具
- 连续天数或完成率产品
- 需要用户自己读懂大量指标的仪表盘
- 伪装成健康陪伴的购买转化漏斗
- 套了健康主题的泛用聊天机器人

## 3. 目标用户

核心用户画像：

- 女性，通常 22-35 岁
- 可能有 Apple Watch 或其他健康数据来源
- 看得到很多原始数值，但不知道这些数值对今天意味着什么
- 想要温和、有用的解释，而不是压力
- 可能记录周期和心情，但不想每天填很多表

核心问题：

> “告诉我今天怎么样，以及我可以轻轻试什么。”

产品优先服务这个问题，再考虑功能广度。

## 4. 产品承诺

Vitora 应该让用户感到：

- “我几秒内就知道今天状态。”
- “Vitora 记得什么对我有用。”
- “我可以很轻地记一笔，不像填表。”
- “这些数据是私密、谨慎处理的。”
- “App 在帮我看见模式，而不是评判我。”

Vitora 不承诺：

- “记录所有事情。”
- “每天都优化到最好。”
- “完成今日健康任务。”
- “解锁一个巨大控制台。”

## 5. P0 Swift MVP 边界

P0 Swift MVP 只保留证明 Vitora 成立的最小闭环：

| Area | P0 Intent |
| --- | --- |
| Onboarding | 收集最小身份、周期上下文、关注点；不要求 WeChat 登录 |
| HealthKit / Data Source | P0 具备 HealthKit 能力，但用户可跳过；app 必须支持手动/低数据模式 |
| Today | 展示现在状态、身体要素、Vitora 今日建议；顶部日历入口解释今天在周期时间线中的位置 |
| Energy / Orb | Energy Ball 进入 P0，但作为每日首次/下拉揭示/晚间复盘的隐藏仪式层，不作为首页常驻主 UI |
| Vitora 今日建议 / 当日意图 | 保留为核心学习动作；建议必须形成当日意图、提醒偏好和晚间复盘路径 |
| Vitora | 提供 AI-native assistant surface、上下文理解、轻校准、输入 dock、语音入口预留和 contextual sheet |
| Cycle | 提供当前周期阶段与今天的关系，以及日/周/月能量动态；不作为日历首页 |
| Evening Review | P0 做最小复盘：对比当天 app 干预前后的效果，帮助用户快速感受到价值 |
| Privacy / Compliance | 本地优先、敏感数据加密、LLM 输入最小化 |

P0 暂不包含：

- 大范围抽屉生态
- 小组件配置
- 深度订阅体系
- 多设备管理深度
- 大量高级图表
- IoT 自动化
- 完整 Vitora 养成玩法
- 本地 LLM 执行细节

本地 Gemma / agentic usage 不进入 P0 实现，但后续产品、数据、隐私、AI 技术规格必须提前保留它会被引入的判断空间。

## 6. Vitora 原则

Vitora 是有职责的陪伴，不是贴在界面上的 mascot。

Vitora 应该：

- 先解释，再建议
- 只给一个或两个小行动
- 只在能改善未来建议时记忆反馈
- 承认不确定性，但不制造紧张
- 没有有用下一步时保持安静
- 避免评判、催促和道德化表达

Vitora 不应该：

- 制造虚假权威感
- 过度解释每个指标
- 用锁功能焦虑推动 VIP
- 用吓人的状态标签
- 变成和 Vitora 核心循环无关的泛助手

## 7. 导航形态

产品仍围绕三个主区域：

| Main Area | Role |
| --- | --- |
| Today | 今日状态和下一步 |
| Vitora | 全局 AI assistant：对话、校准、记录、复盘、解释 |
| Cycle | 长期节律背景和能量动态 |

“我的/设置”是支撑结构。Swift MVP 中，它应明显小于原始抽屉路由池，除非某条路由直接服务隐私、账户、数据所有权或 P0 体验。

当前 RN app 有大量抽屉页面和占位路由。这是范围膨胀证据，不是 P0 目标。

## 8. 合规与隐私立场

合规不是页脚装饰，而是产品信任的一部分。

必须继承：

- 所有健康相关内容使用 `Spec/compliance.md` 中批准的合规标识变体。
- `Spec/compliance.md` 的禁用表达列表是硬约束。
- 敏感健康数据本地优先并加密。
- 发给 LLM 的上下文必须最小化，去除直接识别用户的字段。
- 健康数值不得出现在日志或崩溃输出中。
- 数据导出和账号移除是必需能力，即使 P0 UI 很轻。

本 batch 不重写具体合规文案。新 canonical compliance spec 生成前，继续引用 `Spec/compliance.md`。

## 9. 产品质量门槛

功能进入 P0 必须同时通过这些过滤器：

1. 加强早晨到晚间的学习循环。
2. 能以 Swift 原生、克制、易懂的方式呈现。
3. 不制造打卡、连续天数、红点、未完成压力。
4. 有清晰下一步，或有清晰理由保持安静。
5. 尊重隐私和合规约束。
6. 足够简单，能进入第一版 Swift 规格。

有价值但不够简单的功能进入 P1/P2。
